# Lunax — Architecture Specification

**Status:** Technical design v1.1 · companion to the shipped `Lunax.exe` desktop launcher
**Scope:** Backend / technical contract for a next-generation Minecraft: Java Edition desktop launcher
**Audience:** Core engineers, frontend engineers, security reviewers

### Implementation status

The delivered executable is a **.NET 10 WinForms + WebView2** application (sections 2–13 below describe the equivalent Rust/Tauri production architecture). The native C# implementation maps to those sections as follows:

| Spec area | Shipped implementation |
|---|---|
| Shell / IPC | `src/Program.cs` — frameless WinForms window, `AddHostObjectToScript("bridge", …)`, typed sync methods and `Task<string>` (Promise) methods, JSON payloads, `PostWebMessageAsJson` launch events |
| Authentication | `src/AuthService.cs` — Microsoft v2 device code → XBL → XSTS → Minecraft token, entitlement + profile lookup, refresh-token rotation, DPAPI-encrypted storage in `%LOCALAPPDATA%\Lunax\accounts.json` |
| Launch pipeline | `src/MinecraftService.cs` — Mojang manifest/version/assets/libraries with SHA-1 verification, Fabric/Quilt Meta profile merging (including Maven-style libraries), Java detection (Java 8/17/21/25), JVM flag presets, argument substitution, child process + log tailing |
| Modrinth | `src/ModrinthService.cs` — live `/search` with facets, `/project/{id}/version` version matching, primary-file download with SHA-512 verification, required-dependency recursion, hash-based update checks |
| UI | `index.html` — embedded as a resource, loaded from `https://lunax.local/`, all state in a dedicated WebView2 profile |
| Logo / icon | `logo.png`, `app.ico`, generated by `make-logo.ps1` |

The UI also ships a **flat 2D skin/cape preview** (authentic 64×64 UV mapping rather than a 3D model), fetches the signed-in account's real Mojang skin/cape textures through `getAccountTexture`, and offers a full instance-detail page, large icon navigation with hover tooltips, ambient particles, and a launch-progress overlay.

Verified end-to-end: real Modrinth search/install (`.jar` written into an instance), real device-code issuance, vanilla 1.8.9 launch on Java 8, and Fabric 1.21.11 launch on Java 25 with streamed progress events and process stop. Note: the default Microsoft client ID is a public ID registered to Prism Launcher, which is why the approval page names that app; users can override it with their own Azure application ID in Settings.

## 1. Overview & Design Goals

Lunax is a desktop-native launcher for Minecraft: Java Edition built around four product pillars: obsidian-glassmorphic visuals, a multi-theme engine, first-class modloader (Fabric-first) support, and an integrated Modrinth browser — all wrapped in an instance-isolated, secure-by-default architecture.

### Design goals

| Goal | Requirement |
|---|---|
| **Fast startup** | Cold UI-ready < 400 ms; cached metadata means no network on launch-critical path. |
| **Isolation** | Every profile is a self-contained directory; mods, configs, saves and options never bleed between instances. |
| **Secure credentials** | Microsoft identity tokens never exist in the webview, never touch `localStorage`, and are encrypted at rest in an OS keychain. |
| **Offline capable** | Version manifests, asset indexes and Modrinth search results are cached with TTL + ETag; launch works fully offline for previously prepared instances. |
| **Elastic theming** | Tokens, not hardcoded colors; runtime theme switching without reload via CSS custom properties driven from native theme config. |
| **Smooth interaction** | Spring-physics motion composited on the GPU; 60 fps floor, 120 fps target on high-refresh displays. |

### Non-goals (v1)

- Bedrock Edition support.
- Server/hosting management beyond joining addresses.
- Replacing in-game mod managers; the launcher owns installation, the game owns runtime.

## 2. Technology Stack & Process Model

### Recommendation

**Primary: Tauri 2** — Rust core, system WebView (WWebView2 / WKWebView / WebKitGTK), web frontend (TypeScript + framework-agnostic). Tauri gives us a small binary, a typed IPC boundary, a capability-based permission model, and native keychain/HTTP clients out of the box. The single-file UI prototype maps directly to the Tauri webview layer.

**Secondary: Electron** — viable if the team needs Chromium-only APIs or uniform rendering, at the cost of bundle size (~150 MB) and a Node main process that must still delegate credential work to a native module. Electron would use `contextIsolation: true`, a preload bridge mirroring the same typed command surface, and `safeStorage` for token encryption.

| Layer | Technology |
|---|---|
| Core / domain | Rust 2021, `tokio` async runtime, `reqwest`, `serde`, `sqlx` (optional), `tauri` plugins |
| UI | Web (TS/JS), CSS custom properties, WebGL (three.js) for 3D preview |
| IPC | Tauri commands + events (typed `#[derive(Serialize, Deserialize)]` payloads) |
| Storage | OS keychain + versioned JSON under platform app-data dir |
| Logging | `tracing` + structured JSON, opt-in Sentry-style telemetry |

### Process model

```
┌─────────────────────────────────────────────────────────────────────┐
│                     LUNACHER APPLICATION                            │
├─────────────────────────────────────────────────────────────────────┤
│  ┌──────────────────────┐        ┌───────────────────────────────┐  │
│  │   Webview UI process │◄──IPC──►│  Main / Core process (Rust)   │  │
│  │  - themes, views     │ events │  - domain services            │  │
│  │  - 3D preview        │        │  - auth, tokens, keychain     │  │
│  │  - spring animations │        │  - secure store, permissions  │  │
│  │  NO secrets here     │        └──────────────┬────────────────┘  │
│  └──────────────────────┘                       │ spawn/manage      │
│                                    ┌────────────┼────────────────┐  │
│                                    ▼            ▼                ▼  │
│                            ┌────────────┐ ┌──────────┐ ┌────────────┐│
│                            │ Background │ │  Game    │ │  Game      ││
│                            │ task worker│ │ child #1 │ │ child #2   ││
│                            │ downloads, │ │ (JVM)    │ │ (JVM)      ││
│                            │ hashing,   │ │ isolated │ │ isolated   ││
│                            │ indexing   │ └──────────┘ └────────────┘│
│                            └────────────┘                           │
└─────────────────────────────────────────────────────────────────────┘
```

- **Main/core process (Rust):** owns all privileged state — tokens, filesystem writes, HTTP, process spawning. It is the only component that talks to the OS keychain.
- **Webview UI:** renders the prototype's visual layer. Holds only non-sensitive UI state. Calls typed commands; receives streamed events.
- **Background task worker:** a Tokio task pool (or dedicated thread) for long-running work: asset downloads, SHA checks, mod indexing. Keeps the UI responsive and supports cancellation.
- **Game child processes:** one JVM per launched instance, spawned with a controlled working directory, classpath and JVM flags. Lifecycle (stdin/stdout piping, exit code) is tracked by the core.

### "Core" abstraction

`lunacher-core` contains **no Tauri or UI types**. It exposes async service traits and plain structs (`Account`, `Instance`, `GameVersion`, `ModProject`) so domain logic is testable in isolation and reusable if the shell changes (e.g., a future CLI). The Tauri crate is a thin adapter that validates inputs, calls core services and serializes results/events. All filesystem paths enter core via an injected `AppPaths` provider; nothing is hardcoded to a platform.

## 4. IPC / Command Boundary

### Typed commands

All commands are `async`, input/output are `serde` structs/enums, and every handler returns `Result<T, AppError>`. Commands run on the core service layer; long ones spawn background tasks and stream progress.

| Group | Example commands |
|---|---|
| Accounts | `list_accounts`, `begin_device_login`, `poll_device_login`, `refresh_account`, `remove_account`, `set_active_account`, `create_offline_account` |
| Instances | `list_instances`, `create_instance`, `update_instance`, `delete_instance`, `duplicate_instance`, `toggle_mod`, `export_instance`, `import_instance` |
| Launch | `prepare_instance`, `launch_instance`, `stop_instance`, `list_running_instances` |
| Modrinth | `search_projects`, `get_project`, `get_project_versions`, `install_modrinth_project`, `check_updates`, `import_mrpack`, `export_mrpack` |
| Wardrobe | `list_skins`, `set_skin`, `list_capes`, `preview_player`, `validate_skin_png` |
| System | `get_theme`, `set_theme`, `get_runtime_info`, `open_path`, `get_permission_status` |

### Streaming events

Progress is emitted as typed events; the UI subscribes per-operation with a correlation `job_id`:

```
download_progress { job_id, path, bytes_done, bytes_total, speed_bps }
install_progress  { job_id, stage: Fetching|Hashing|Extracting|Writing, item }
launch_status     { job_id, instance_id, stage: Preparing|Downloading|Starting|Running|Exited, pid?, exit_code? }
auth_poll         { flow_id, state: Pending|SlowDown|Expired|Success|Denied }
log_line          { instance_id, level, message }   # game stdout/stderr tail
```

### Cancellation

Each long operation returns a `job_id` immediately. `cancel_job(job_id)` sets an `AtomicBool`/`CancellationToken` checked at chunk boundaries; partial downloads are written to `.part` files and discarded on cancel. Game processes are terminated via `stop_instance(instance_id)` (graceful `SIGTERM`/`CloseMainWindow`, then kill after timeout).

### Error model

```rust
pub enum AppError {
  Network { status: Option<u16>, message: String, retryable: bool },
  Auth { kind: Expired|Denied|Pending|DeviceCodeExpired, provider: &'static str },
  Integrity { path: String, expected: String, actual: String }, // sha mismatch
  Filesystem { path: String, source: String },
  Validation { field: String, message: String },
  Cancelled { job_id: String },
  Conflict { resource: String, message: String },
}
```

Every error serializes with a stable `code`, human message, and optional `retry_after`. The UI maps codes to localized strings; raw errors go to structured logs only.

## 5. Authentication — Microsoft Xbox Live OAuth 2.0 Device Code Flow

Lunax uses the **device-code flow** (no embedded credential form, no redirect URI interception), which resists phishing and works on headless setups. The flow is orchestrated entirely in the Rust core; the renderer receives only a user code and a flow state.

### Flow (exact endpoints)

1. **Device code request**
   `POST https://login.live.com/oauth20/devicecode`
   body: `client_id=<azure-app-id>&scope=XboxLive.signin offline_access&response_type=device_code`
   → `{ user_code, verification_uri, device_code, expires_in, interval }`.
   UI shows `user_code` + link; user approves at `https://www.microsoft.com/link` (verification URI).

2. **Poll for token**
   `POST https://login.live.com/oauth20/token` with `grant_type=urn:ietf:params:oauth:grant-type:device_code`, `device_code`, `client_id`.
   Handle `authorization_pending`, `slow_down`, `expired_token`, `access_denied` per spec; honor `interval` backoff. This yields the **Microsoft access token** and a **refresh token**.

   > (Legacy/embedded fallback only: `https://user.login.live.com/ppsecure/post.srf` is a login-form endpoint used by old launchers. It is **not** used by Lunax — device code is the supported path. It is documented here so reviewers recognize the historical surface and confirm its exclusion.)

3. **Xbox Live authenticate**
   `POST https://user.auth.xboxlive.com/user/authenticate`
   body: `{ "Properties": { "AuthMethod": "ProofOfPossession", "Id": "opt:<uuid>", "DeviceType": "Android", "Version": "10", "Claims": { "user_tokens": { "microsoft": "<ms_access_token>" } } }, "RelyingParty": "http://auth.xboxlive.com", "TokenType": "JWT" }`
   → `uxs` token + `xuid`.

4. **XSTS authorize**
   `POST https://xsts.auth.xboxlive.com/xsts/authorize`
   body: `Claims: { "user_tokens": { "xbl": "<uxs>" } }, RelyingParty: "rp://api.minecraftservices.com/", TokenType: "JWT"`.
   → XSTS token. Handle `2148916233` (no Xbox account), `2148916238` (minor) explicitly.

5. **Minecraft token**
   `POST https://api.minecraftservices.com/authentication/login_with_xbox`
   body: `{ "identityToken": "XBL3.0 x=<uhs>;<xsts_token>" }`
   → Minecraft **access token** + expiry.

6. **Entitlement + profile + skin**
   - `GET https://api.minecraftservices.com/entitlements/mcstore` (Bearer MC token) — verify the `product_minecraft` entitlement.
   - `GET https://api.minecraftservices.com/minecraft/profile` — UUID, skin, cape.
   - `GET https://api.minecraftservices.com/minecraft/profile/skins` — skin history (for wardrobe).
   - `GET https://sessionserver.mojang.com/session/minecraft/profile/<uuid>` — signed skin/cape textures for classic offline-style resolution.

### Refresh & storage

- Refresh via `POST https://login.live.com/oauth20/token` with `grant_type=refresh_token` (long-lived refresh token, rotated on use). Proactive refresh at T-5 min with single-flight locking to avoid duplicate refreshes.
- **At rest:** access + refresh tokens are encrypted and stored in platform keychains — Windows Credential Manager (DPAPI-backed) via `windows-creds`, macOS Keychain via `security-framework`, Linux Secret Service via `secret-service`/`zbus` (fallback: DPAPI-equivalent encrypted file with OS-derived key). The app-data JSON stores only non-secret metadata (`uuid`, `username`, `expires_at`, `xuid`, token *key* handle).
- **No tokens in the webview.** The renderer receives an `account_id` and display name only; launch injection happens in-core.
- **CSRF/state:** device-code flow carries no browser redirect, so `state` is not applicable in the classic sense; each flow still generates an internal `flow_id` + random nonce bound to the in-flight poll to prevent event injection across flows. The `client_id` is registered with PKCE-compatible config where supported.
- **Offline accounts:** created with a username only; UUID is derived; they **cannot** join authenticated servers, use skins/capes from Mojang, or refresh. The UI labels them clearly. Offline UUID derivation and `user_type=mojang` legacy behavior are preserved for LAN/local compatibility.

### Data flow summary

```
UI: begin_device_login → core → Live devicecode → event {user_code, flow_id}
UI: polls via poll_device_login(flow_id)
core: Live token → XBL → XSTS → MC token → entitlement/profile/skin
core: encrypt + store tokens in keychain; write account metadata to app data
core: emit auth_poll {Success, account_id}; UI updates account switcher
```

## 6. Game Asset & Runtime Pipeline

### Version discovery

- Manifest: `GET https://piston-meta.mojang.com/mc/game/version_manifest_v2.json` → `{ latest, versions[] }` with `id`, `type`, `url`, `sha1`, `complianceLevel`.
- Per-version JSON (from `versions[].url`): asset index, libraries (with `downloads.artifact` + `natives`), `mainClass`, `arguments`/`minecraftArguments`, Java `version` requirement.
- Asset index JSON: `objects` map of logical name → `{ hash, size }`; content-addressed at `https://resources.download.minecraft.net/<h[0:2]>/<hash>`.
- Libraries: `https://libraries.minecraft.net/...` plus Fabric/Quilt/NeoForge repositories. Natives extracted to a per-instance `natives/` dir with `.so`/`.dll`/`.dylib` exclusion rules from the version JSON.

### Java runtime detection & pairing

| Minecraft line | Java |
|---|---|
| 26.x and newer | Java 25 |
| 1.21.x | Java 21 |
| 1.18–1.20.x | Java 17 |
| 1.17 | Java 17 |
| 1.13–1.16.x | Java 8 (11 tolerated) |
| ≤1.12 | Java 8 |

Detection scans known install locations + registry + `JAVA_HOME`, reads `java -version`, and pairs per instance with user override. Bundled runtimes (Mojang JRE) can be fetched for exact parity.

### Download, verification & cache

- All downloads run through the background worker with concurrency limits and resume (`.part` files).
- **SHA-1 verification** against manifest/index hashes before commit to cache; mismatch → discard + retry/backoff, surface `Integrity` error.
- Cache layout: `assets/objects/<hash>`, `libraries/<path>`, `versions/<id>.json`, `runtimes/<java>/`. ETag/Last-Modified based revalidation with TTL; `--offline` uses cache only.
- Prepared instances launch with **zero network calls**.

### Modloaders

- **Fabric:** `GET https://meta.fabricmc.net/v2/versions/loader`, `/v2/versions/game`, and `POST https://meta.fabricmc.net/v2/versions/loader/<game>/<loader>/profile/json` (also `GET .../profile/json`) → launch profile with libraries + `mainClass`.
- **Quilt:** `https://meta.quiltmc.org/v3/versions/loader`, `/v3/versions/game`, `.../profile/json`.
- **NeoForge:** `https://maven.neoforged.net/releases/net/neoforged/neoforge/maven-metadata.xml` (version list) + installer/small launcher profile; Forge legacy uses `https://files.minecraftforge.net/net/minecraftforge/forge/maven-metadata.json`.
- Loader profile is merged into the version JSON before classpath generation.

### Classpath & JVM arguments

Classpath = all library `paths` + natives dir + version jar + loader libraries, in deterministic order with OS path separator. Final command:

```
java <jvm_args> -cp <classpath> <mainClass> <game_args>
```

- **Aikar's flags** (with ZGC variant for Java 17+): `-XX:+UseG1GC -XX:+ParallelRefProcEnabled -XX:MaxGCPauseMillis=200 -XX:+UnlockExperimentalVMOptions -XX:+DisableExplicitGC -XX:+AlwaysPreTouch -XX:G1HeapRegionSize=4M -XX:G1ReservePercent=20 -XX:InitiatingHeapOccupancyPercent=15` — for newer Java, swap to `-XX:+UseZGC -XX:+ZGenerational`.
- Memory from instance settings (`-Xms`/`-Xmx`), defaults sized from system RAM.
- Game args: `--username`, `--uuid`, `--accessToken` (injected in-core, never echoed to logs/UI), `--version`, `--gameDir`, `--assetsDir`, `--assetIndex`, `--versionType`, `--userType`, `--clientId`.
- Working directory is the instance dir; stdout/stderr are piped as `log_line` events to the UI console.

## 7. Modrinth v2 API Integration

Base: `https://api.modrinth.com/v2`. All requests send `User-Agent: Lunax/<version> (contact)`; authenticated endpoints use an optional Modrinth token entered by the user and stored in the keychain.

### Endpoints used

| Endpoint | Purpose |
|---|---|
| `GET /project/{id_or_slug}` | Project metadata (title, description, icon, body, download counts) |
| `GET /search?query=...&facets=...&limit=...&offset=...&sort=...` | Discover mods/resource packs/shaders |
| `GET /project/{id}/version?loaders=["fabric"]&game_versions=["1.21.1"]` | Compatible versions |
| `GET /version/{id}` / `GET /version/{id}/file` | Version metadata / primary file (url, hashes, size, filename) |
| `GET /tag/category`, `/tag/loader`, `/tag/game_version` | Filter chips + facets |
| `GET /project/{id}/dependencies` | Dependency graph |
| `POST /version_file` (hash lookup) | Bulk hash → version resolution for updates |

### Search facets syntax

Facets are a JSON array of arrays; `[]` within outer array = OR, across outer arrays = AND:

```
facets=[["categories:fabric"],["versions:1.21.1"],["project_type:mod"]]
```

Lunax builds these from UI filter chips, URL-encodes them, and debounces keystrokes (250 ms) with request caching keyed by the normalized query.

### Hash-based updates

Files provide `hashes.sha1` / `hashes.sha512`. The launcher hashes installed `.jar` files locally (SHA-512) and compares, or bulk-posts hashes to `POST /version_file`. Update badges appear when a newer compatible version exists; users can one-click update with dependency re-resolution.

### Dependency resolution

For each version, `dependencies[]` entries are `{project_id, version_id?, type: required|optional|incompatible, dependency_type}`.
- **required** → auto-install (recursively, cycle-guarded), with explicit user confirmation of the full set before write.
- **optional** → shown with checkboxes; default off.
- **incompatible** → block install with explanation.
Resolutions are checked against the instance's loader + game version facets.

### `.mrpack` import/export

Spec: ZIP with `modrinth.index.json` (`formatVersion: 1`, `game`, `versionId`, `name`, `summary`, `dependencies: {minecraft, fabric-loader}`, `files[]` with `path`, `hashes.sha1/sha512`, `env`, `downloads`). Optional `overrides/` (configs, resourcepacks, shaderpacks) and `server-overrides/`.
- **Import:** parse index, verify each file hash, download into instance dirs, apply overrides, then report missing/unsupported deps.
- **Export:** walk instance dirs, hash installed files, produce index + overrides, honoring `.gitignore`-style exclude rules.

### Install targets

| Content | Instance directory |
|---|---|
| Mods | `mods/` |
| Resource packs | `resourcepacks/` |
| Shaders | `shaderpacks/` |

When a shader pack is installed but Iris/OptiFine is absent, core emits `shader_needs_loader {instance_id, suggested: "iris"}`; the UI prompts to auto-install the matching Iris version via the loader pipeline.

## 8. Instance Model

### Per-instance layout

```
instances/<slug>/
├── instance.json          # schema (below)
├── mods/                  # enabled *.jar + disabled *.jar.disabled
├── resourcepacks/
├── shaderpacks/
├── config/
├── saves/
├── options.txt
├── natives/               # extracted JNI libs (regenerated)
└── logs/latest.log
```

`instance.json` (schema versioned):

```json
{
  "schema": 2,
  "id": "uuid",
  "name": "Fabric 1.21.1 — Main",
  "gameVersion": "1.21.1",
  "loader": { "type": "fabric", "version": "0.16.9" },
  "accountId": "account-uuid-or-null",
  "java": { "path": "/path/to/java", "version": 21 },
  "memoryMb": { "min": 2048, "max": 6144 },
  "jvmArgs": ["-XX:+UseZGC"],
  "createdAt": "...", "updatedAt": "...",
  "content": {
    "mods": [{ "projectId": "...", "versionId": "...", "file": "mods/x.jar", "sha512": "..." }]
  }
}
```

### Behavior

- **Profile ↔ account linking:** `accountId` selects which authenticated identity is injected at launch; per-instance override is allowed. Unlinking falls back to active account or offline mode.
- **Enable/disable mods:** atomic rename `mod.jar` ↔ `mod.jar.disabled`. The index tracks both; disabled jars excluded from classpath discovery by the game naturally (extension not `.jar`).
- **Export/import:** export zips `instance.json` + selected dirs (+ optional saves); import validates schema, migrates if needed, and writes into a fresh slug to avoid collisions.
- **Isolation guarantees:** separate cwd, separate `mods/config/saves/options.txt`, no launcher-level symlinks to shared dirs. Caches (`assets`, `libraries`) are shared read-only content-addressed stores — a downloaded file is immutable and hash-verified, so sharing cannot corrupt an instance.

## 9. Skin & Cape Wardrobe

### Mojang endpoints

- `GET https://api.minecraftservices.com/minecraft/profile` — current skin/cape.
- `POST https://api.minecraftservices.com/minecraft/profile/skins` — set skin (`{variant, texture: dataURL-ish base64}`); requires Bearer MC token (core-side).
- `DELETE https://api.minecraftservices.com/minecraft/profile/skins` — reset to default (core-side).
- `GET .../minecraft/profile/skins` — skin history for wardrobe listing.
- Cape endpoints historically `PUT .../minecraft/profile/capes/active` / `DELETE .../capes/active` for cape selection where available; if a user has no capes, show empty state.
- Face/avatar fallback: `https://crafatar.com/avatars/<uuid>` / `https://api.mineatar.io/face/<uuid>` style services (configurable, opt-in) with local cached PNG fallback and a procedural identicon when offline.

### Local validation

- Accept PNG only; decode and require dimensions **64×64** (or **64×32** legacy → convert to 64×64 by extending legs). Reject > 1 MB or non-PNG.
- Detect **slim** model flag (Alex) via alpha channel at pixel `(54, 20)`-region heuristics or explicit user choice; store `slim: bool`.
- Store wardrobe files in native app data (`appdata/wardrobe/<account_id>/skins/*.png`), **never** in webview storage. Each account has its own wardrobe; switching accounts swaps available skins.

### 3D preview

- Render a box-based player model in **WebGL via three.js**: composite geometry for head (8×8×8), body (8×12×4), arms (4×12×4), legs (4×12×4), slim arms (3×12×4). UV map to the 64×64 texture atlas using standard Minecraft coordinates (head `0,0`, body `16,16`, arm `40,16`, leg `0,16`, plus overlay layers with slight scale offset).
- Orbit camera, idle breathing animation via spring-driven transforms, shadow/ground plane. Provide a **software-rendered fallback** (2D canvas box projection) for WebGL-less environments.

## 10. State & Persistence

### Webview `localStorage` (non-sensitive only)

- Active theme id, accent, glass/blur intensity, reduced-motion flag, sidebar layout, last-opened view, language, UI-scale.
- In-memory caches of Modrinth search pages and icon URLs (expire on reload).
- **Never** tokens, UUIDs tied to secrets, refresh tokens, or private file paths.

### Native app data (authoritative)

- `accounts.json` — account metadata + keychain handles.
- `instances/<id>/instance.json` — per-instance config.
- `wardrobe/` — skins/capes by account.
- `cache/` — manifests, version JSONs, assets (content-addressed), Modrinth responses.
- `settings.json` — launcher-wide settings, update channel, telemetry consent.
- `audit.log` — structured security events.

Platform roots: `%APPDATA%\Lunax` (Windows), `~/Library/Application Support/Lunax` (macOS), `$XDG_DATA_HOME/lunacher` (Linux).

### Versioning & migrations

- Every JSON file carries `schema: n`. On startup, core runs ordered migrations `1→2→3…` in a single transaction-like pass, backing up originals to `backups/<timestamp>/` before writing. Unknown future schema → fail closed with an explicit "update required" message.

### Atomic writes & backup

- Write to `<file>.tmp` → `fsync` → `rename` over target (atomic on same volume); preserve permissions. Maintain rolling backups of config/accounts (not the large asset cache). Daily backup of `instance.json` + `settings.json`; user-triggered full export produces a portable archive.

## 11. Security & Privacy

| Control | Implementation |
|---|---|
| Consent | First-run consent screen; telemetry opt-in (default off); explicit consent for Modrinth token use. |
| Scoped OAuth | Only `XboxLive.signin offline_access`; no broad Microsoft Graph scopes. |
| Token encryption | Keychain at rest; encrypted in memory where feasible; zeroized after use. Never in renderer/localStorage/logs. |
| Renderer isolation | Tauri capabilities grant only needed plugins; no arbitrary FS write from webview; `open_path` allow-listed to instance dirs. |
| CSP | Strict `default-src 'self'`; `connect-src` limited to configured API origins via Tauri HTTP plugin; no `unsafe-inline` in production, no remote script loading. |
| Sandboxing | Webview sandbox enabled; game processes run with cwd = instance dir and least-privilege environment; secrets passed via argv only at spawn (documented residual risk). |
| Audit logging | Log auth flow start/success/failure, account add/remove, token refresh, instance export, mod install from untrusted source. Logs redact tokens, codes and UUIDs-as-secrets. |
| Rate limits | Client-side throttle on OAuth polling (`interval`), Modrinth requests (respect `X-RateLimit`), and file-hashing concurrency. |
| Phishing-resistant copy UUID | UUID copy button shows a confirmation ("Copy UUID — safe to share?") and never copies tokens/access codes; clipboard content is only public profile identifiers. |
| Safe account removal | Remove account = delete keychain entries + metadata + wardrobe for that account; keep instances but unlink; confirmation lists consequences. Refresh tokens revoked via Live revocation endpoint when possible. |
| Supply chain | Verify sha1/sha512 for all downloads; refuse loader profiles from non-allowlisted hosts; signature checks on updater artifacts. |

Residual risk: passing `--accessToken` in JVM argv is visible to local process inspection — standard Minecraft behavior; documented and mitigated by short token lifetimes and no token logging.

## 12. Performance & Animation Notes

- **CSS variables + spring physics:** theme tokens (`--bg`, `--glass`, `--accent`, `--radius`, `--blur`) drive all visuals; theme switch animates variables via registered custom properties or a short crossfade. Motion uses a spring solver (`stiffness`, `damping`, `mass`) rather than fixed easing for natural feel; honor `prefers-reduced-motion` by snapping to final state.
- **GPU compositing:** animate only `transform` and `opacity`; `will-change` applied sparingly; blur/backdrop-filter limited to static panels to avoid per-frame repaint. Glass layers use pre-blurred textures where possible.
- **Virtualization:** mod/resource lists use windowed rendering (react-window-style) so 5,000+ entries stay smooth; rows are fixed-height with skeleton placeholders during fetch.
- **Debounced search:** 250 ms debounce + stale-request cancellation (`AbortController` in UI, job cancellation in core) + LRU response cache.
- **Request caching:** HTTP cache with ETag/TTL for Modrinth and Mojang metadata; thumbnail cache keyed by URL/hash; background prefetch of likely-next view.
- **Targets:** UI-ready < 400 ms; interaction latency < 16 ms (60 fps) with 120 fps on high-refresh displays; launch prep (cached) < 1 s; no animation frame drops during download progress updates (throttle events to ~30 Hz and coalesce in UI).

## 13. Testing, Observability & Rollout

### Testing

- **Unit:** Rust tests for auth payload construction, classpath ordering, Java pairing, facet building, facet/JSON schema parsing, skin PNG validation, `.mrpack` parsing.
- **Integration:** mock HTTP servers (Mojang, Fabric, Modrinth, Live/XSTS) with recorded fixtures; temp-dir instances; assert atomic writes and migration idempotence.
- **E2E:** Tauri webview driver (or Playwright against a dev shell) covering login simulation, instance create → launch → stop, mod install → toggle → export.
- **Contract tests:** JSON schemas for `instance.json` and all IPC payloads checked in CI.
- **Security tests:** assert no secrets in logs/localStorage snapshots; CSP violation tests; keychain absence handling.

### Observability

- `tracing` structured JSON logs with `trace_id` per job; levels filtered by channel.
- Telemetry opt-in only: anonymous counters (launch success, crash, feature usage) with no identifiers; clear privacy notice.
- Crash reporting: minidump + last 200 log lines, uploaded only with consent; symbol upload in CI.
- Local "Diagnostics" view exporting a redacted support bundle.

### Rollout

- Channels: **stable**, **beta**, **nightly** with signed updater artifacts and staged rollout percentages.
- Feature flags for experimental loaders/UI; kill switch for telemetry and risky features.
- Release gate: all tests green, no high/critical security findings, performance budget verified on reference hardware.
